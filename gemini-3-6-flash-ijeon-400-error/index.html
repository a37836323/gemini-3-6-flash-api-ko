이 페이지의 가격 및 모델 정보는 변경되었을 수 있습니다. 최신 요금은 OpenLux 요금 페이지에서 확인하세요.

홈 ／ Gemini 3.6 Flash

gemini-3.6-flash 이전 후 HTTP 400이 날 때: 공식 체크리스트에 따른 항목별 수정

gemini-3-flash-preview나 gemini-3.5-flash를 gemini-3.6-flash로 바꾼 뒤 요청이 HTTP 400을 반환한다면 먼저 두 가지를 확인하세요. 요청의 마지막이 미리 채워 둔 model 턴(프리필)으로 끝나지 않는지, 그리고 thinking_level과 thinking_budget을 동시에 보내고 있지 않은지입니다. Google 공식 페이지 「What's new in Gemini 3.6 Flash and 3.5 Flash-Lite」(https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.6, 2026-10-13 업데이트)는 요청에서 비어 있지 않은 마지막 턴이 model 턴이면 API가 400 오류를 반환한다고 명시합니다. 같은 페이지에는 temperature, top_p, top_k가 지원 중단되어 무시되며, 향후 모델 세대에서는 이 값을 보내면 HTTP 400이 반환된다는 내용도 있습니다. 마이그레이션 체크리스트는 candidate_count 제거, thinking_budget을 thinking_level로 교체, 함수 호출 코드 점검도 요구합니다. 아래에서는 Google 문서에 따라 항목별로 확인하고, 마지막으로 수정이 제대로 되었는지 확인하는 방법을 설명합니다.

영향을 받는 코드

지원 중단 모델 페이지(https://ai.google.dev/gemini-api/docs/deprecations, 2026-10-22 업데이트)는 gemini-3-flash-preview와 gemini-3.5-flash의 권장 대체 모델로 gemini-3.6-flash를 제시합니다. gemini-3.5-flash에 대해서는 엔드포인트가 종료되지 않고 API 요청을 자동으로 gemini-3.6-flash로 라우팅하며, Google AI Studio에서는 이 모델을 선택할 수 없다는 설명이 붙어 있습니다.

즉 Google API를 직접 호출하면서 코드에 아직 gemini-3.5-flash를 지정하고 있더라도, 요청은 이미 gemini-3.6-flash가 처리하고 있습니다. 이 페이지에서 다루는 규칙은 그런 코드에도 해당합니다.

새 기능 페이지는 현재 gemini-3.6-flash와 gemini-3.5-flash-lite를 Gemini 3 시리즈의 이전 세대 릴리스이며 프로덕션에서 계속 사용할 수 있는 모델로 설명하고, 최신 Flash 모델로는 Gemini 3.8 Flash를 안내합니다. 지원 중단 모델 페이지에는 gemini-3.6-flash의 종료일이 발표되어 있지 않습니다. 공식 가이드는 Gemini 3.5 Flash, Gemini 3 Flash(Preview), Gemini 3.1 Pro에서 3.6 Flash로의 이전을 다룹니다.

Google에 따르면 이러한 API 변경은 Gemini 3.6 Flash와 Gemini 3.5 Flash-Lite, 그리고 이후 출시되는 모든 Gemini 모델에 적용됩니다. 따라서 여기서 한 수정은 더 새로운 모델로 옮길 때도 그대로 유지하는 편이 안전합니다.

model 턴 프리필이 400을 일으키는 경우

공식 가이드에 따르면 model 턴 프리필은 더 이상 지원되지 않습니다. 요청에서 비어 있지 않은 마지막 턴의 역할이 model이면 API는 400 오류를 반환합니다. 프리필이란 contents 끝에 model 역할의 턴(예: JSON 객체의 시작 부분)을 넣어 모델이 그 뒤를 이어 쓰게 하는 기법입니다.

이 규칙이 보는 것은 비어 있지 않은 마지막 턴뿐입니다. user와 model 턴이 번갈아 나오는 일반적인 대화 기록은 비어 있지 않은 마지막 턴이 model이 아니라면 문제가 없습니다.

Google은 대안으로 두 가지를 제시합니다. 형식이나 어조에 관한 요구 사항을 system_instruction에 적는 방법과, Structured outputs(https://ai.google.dev/gemini-api/docs/structured-output)로 응답 형식을 제한하는 방법입니다. JSON을 얻으려고 프리필을 썼다면 Structured outputs로 바꿀 수 있습니다.

원인을 가려내려면 실제로 API에 전송되는 요청 본문을 로그로 남기고, contents의 비어 있지 않은 마지막 턴이 model인지 확인하세요. 중간 라이브러리를 사용한다면 직접 작성한 코드뿐 아니라 그 라이브러리가 보내는 본문도 확인해야 합니다.

temperature, top_p, top_k와 candidate_count

마이그레이션 가이드에 따르면 temperature, top_p, top_k는 지원 중단되었으며 API가 무시합니다. 향후 모델 세대에서는 이 파라미터를 보내면 HTTP 400이 반환되므로, 모든 요청에서 제거하라고 안내합니다. 3.6 Flash에서는 현재 오류가 나지는 않지만 효과도 없습니다.

실무적으로는 응답을 안정시키려고 temperature를 0으로 두었던 코드가 3.6 Flash에서는 그 효과를 얻지 못한다는 뜻입니다. 결정성을 높이고 싶다면, Google은 사용 사례에 맞는 명확한 규칙을 담은 system instruction을 정의하라고 권장합니다.

체크리스트는 candidate_count 제거도 요구합니다. Google에 따르면 candidate_count는 Gemini 3 이후 지원되지 않습니다.

참고로 Gemini 3 개발자 가이드(https://ai.google.dev/gemini-api/docs/gemini-3)는 현재 「지원 중단되었으며 삭제될 예정」이라고 표시되어 있지만, temperature를 기본값 1.0으로 유지할 것을 강력히 권장하고, 1.0 미만으로 낮추면 반복(looping)이나 성능 저하 같은 예기치 않은 동작이 생길 수 있다고 경고했습니다. 3.6 Flash 마이그레이션 가이드는 그보다 새로운 지침으로, 이 파라미터들을 그냥 제거하도록 합니다.

thinking_budget을 thinking_level로 교체하기

체크리스트는 thinking_budget을 thinking_level로 바꾸라고 하며, 값으로 medium 또는 high를 제시합니다. 공식 Thinking 페이지(https://ai.google.dev/gemini-api/docs/thinking)의 표에서 gemini-3.6-flash는 사고가 기본적으로 켜져 있고(medium), minimal, low, medium, high 수준을 지원합니다. 이 표에는 이 모델의 사고를 끄는 옵션이 나와 있지 않으며, 가장 낮은 수준은 minimal입니다.

gemini-3-flash-preview에서 옮기는 경우 기본값에 주의하세요. 같은 표에서 gemini-3-flash-preview의 기본값은 high, gemini-3.6-flash의 기본값은 medium입니다. 코드에서 사고 수준을 지정하지 않고 기본값에 맡겼다면, 전환 후 실제 수준이 high에서 medium으로 내려갑니다. 이전 동작을 유지하려면 high를 명시하세요. gemini-3.5-flash에서 옮기는 경우에는 기본값이 바뀌지 않습니다. Google은 3.6 Flash가 3.5 Flash와 같은 medium을 기본 사고 수준으로 사용한다고 설명합니다.

지원 중단된 Gemini 3 가이드에는 thinking_budget이 하위 호환을 위해 계속 지원되지만, thinking_level과 기존 thinking_budget을 같은 요청에서 함께 쓸 수 없으며 그렇게 하면 400 오류가 반환된다고 적혀 있습니다. 새 필드를 추가했다면 둘 다 보내지 말고 이전 필드를 삭제하세요.

Google 예제는 Interactions API를 사용하며, 사고 수준을 generation_config 안의 thinking_level 필드로 지정합니다. generateContent에서는 사고 관련 필드의 이름이나 위치가 다를 수 있으므로, Interactions API 예제의 필드 이름을 그대로 가져다 쓰지 말고 API 레퍼런스(https://ai.google.dev/api/generate-content)의 GenerationConfig를 확인하세요.

함수 호출과 thought signature에서 확인할 점

체크리스트는 함수 호출 코드를 점검하라고 요구합니다. 첫째, 멀티모달 에셋을 응답 페이로드(response payload) 안에 넣는 것입니다. Function calling 페이지(https://ai.google.dev/gemini-api/docs/function-calling)에 따르면 Gemini 3 시리즈 모델에서는 function_result 단계의 result 필드에 하나 이상의 콘텐츠 블록을 넣어 보낼 수 있고, 각 블록에는 text나 image 같은 type을 지정해야 합니다.

둘째, 인라인 지시를 줄바꿈 두 개(\n\n)로 구분해 형식을 맞추는 것입니다. 공식 체크리스트에는 이 이상의 설명이 없습니다.

셋째, Malformed_Function_Call입니다. Function calling 페이지에 따르면 도구 호출 직전에 구조화된 텍스트(XML, YAML, JSON 등)를 출력하도록 프롬프트에서 요구하면, 그 도구 호출이 가끔 Malformed_Function_Call로 실패할 수 있습니다. 권장 대처는 도구 호출 전 메모를 일반 텍스트가 아니라 전용 update 함수 호출에 담도록 모델에 지시하는 것입니다. update 함수는 previous_step, plan, next_step, external 네 개의 STRING 타입 파라미터를 가지며, 네 개 모두 필수로 선언합니다. 대안으로는 메모를 Markdown 제목(# UPDATE, ## PLAN 등)으로 쓰게 하거나, 도구 호출 전에 텍스트 출력을 요구하지 않는 두 가지 방법이 제시되어 있습니다.

thought signature에 대해 Function calling 페이지는 SDK가 자동으로 처리한다고 설명합니다. 대화 기록을 직접 관리하는 경우(무상태 모드), Thinking 페이지에 따르면 모든 thought 블록을 받은 그대로 다시 보내야 하며, 기록에서 삭제하거나 수정하면 안 됩니다. 세션 도중 모델을 바꾸는 경우에도 마찬가지입니다. 상태 저장 모드(store를 true로 설정하고 이후 턴에서 previous_interaction_id를 전달)에서는 signature와 관련해 따로 할 일이 없습니다. API 레퍼런스에는 종료 사유 MISSING_THOUGHT_SIGNATURE도 있으며, 「요청에 thought signature가 하나 이상 누락됨」이라고 설명되어 있습니다. 이 값이 나오면 기록에서 thought 블록이 빠지지 않았는지 확인하세요.

오류 메시지 없이 바뀌는 동작

마이그레이션 가이드에 따르면 3.6 Flash는 Gemini 3.5 Flash보다 변경을 가하기 전에 진단용 스크립트를 먼저 실행하는 경우가 더 잦습니다. Google은 이것이 복잡한 작업에서 정확도를 높이지만, 일상적인 프런트엔드 작업에서는 탐색 단계가 늘어날 수 있다고 설명합니다.

또한 시각적 레이아웃과 스타일링에 대해서는 사람 평가자들이 이전 모델을 더 선호했다고 합니다. Google은 명확한 디자인 가이드라인을 제공하면 이를 완화할 수 있다고 말합니다.

Google은 3.6 Flash가 Gemini 3.5보다 더 적은 추론 단계, 대화 턴, 도구 호출로 다단계 워크플로를 완료한다고도 설명합니다. 이것이 사용량에 영향을 주는지는 직접 청구 데이터로 확인하세요. 요금은 OpenLux 요금 페이지에서 확인하세요.

수정이 되었는지 확인하는 방법

1단계: /v1/models 엔드포인트를 호출해 목록에 gemini-3.6-flash가 있는지 확인합니다. 그다음 애플리케이션 코드가 실제로 새 모델 이름을 사용하는지 확인합니다.

2단계: 비어 있지 않은 마지막 턴이 user이고, temperature, top_p, top_k, candidate_count를 포함하지 않으며, 사고 파라미터는 하나(thinking_level)만 있는 최소 요청을 보냅니다. 상태 코드 200과 본문이 있는 응답이 오고, 이전의 400 오류가 더 이상 나지 않는지 확인합니다.

3단계: 사고 수준이 실제로 적용되는지 확인합니다. generateContent 응답에서는 usageMetadata.thoughtsTokenCount 필드가 사고 토큰 수를 나타냅니다(Interactions API에서는 total_thought_tokens로 반환됩니다). 같은 프롬프트를 low와 high로 한 번씩 보내 값을 비교하면 설정이 모델에 전달되는지 알 수 있습니다.

4단계: 프리필을 Structured outputs로 바꿨다면 실제 입력 예시 몇 개로 응답이 기대한 대로 파싱되는지 확인합니다. 함수 호출을 쓴다면 여러 번의 도구 호출이 포함된 흐름을 끝까지 실행해 Malformed_Function_Call과 MISSING_THOUGHT_SIGNATURE가 모두 나타나지 않는지 확인합니다.

OpenLux 중계로 호출할 때 주의할 점

OpenLux 요금 엔드포인트에는 현재 gemini-3.6-flash가 판매 중으로 표시되며, gemini-3.5-flash, gemini-3-flash-preview, gemini-3.8-flash 등도 판매 중으로 표시됩니다.

지원 중단 모델 페이지에 있는 gemini-3.5-flash에서 gemini-3.6-flash로의 자동 라우팅은 Google 자체 API의 동작입니다. 중계를 통해 gemini-3.5-flash를 지정했을 때 어느 버전이 응답하는지는 이 페이지에서 확인하지 않았습니다. 이전할 때는 모델 이름을 직접 gemini-3.6-flash로 바꾸고 위 체크리스트를 적용해 동작을 명확하게 하세요.

Gemini 네이티브 형식의 요청 경로는 /v1beta/models/gemini-3.6-flash:generateContent이며, OpenAI 호환 엔드포인트도 있습니다. Google 예제가 사용하는 Interactions API(/v1beta/interactions)는 중계에서 확인된 엔드포인트에 포함되지 않으므로 동작한다고 가정하지 마세요. OpenAI 호환 형식에서 사고 파라미터가 필드별로 모델에 어떻게 전달되는지도 확인하지 않았습니다. 앞 섹션의 방법대로 최소 요청과 사고 토큰 수로 직접 확인하세요.

키는 OpenLux 콘솔의 토큰 페이지에서 만듭니다. 요금은 OpenLux 요금 페이지에서 확인하세요.
